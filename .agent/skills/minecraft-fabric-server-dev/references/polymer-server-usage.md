# Polymer 서버 전용 사용 패턴 (1.21.8)

## 목차

1. Polymer 적용 목적
2. 설계 원칙
3. 권장 코드 구조
4. 구현 루프
5. 성능/안정성 검증
6. 운영 장애 패턴

## 1) Polymer 적용 목적

- 클라이언트 모드 설치를 강제하지 않고 서버 측에서 시각/상호작용 표현을 제공한다.
- 핵심 게임 로직은 서버 기준으로 유지하고, 표현 계층만 분리한다.

## 2) 설계 원칙

1. 서버 상태가 진실(SSOT)
2. Polymer는 표현 변환 계층
3. 게임 규칙과 렌더 표현의 결합 금지

간단히 말해:
- `core`가 망가지면 게임이 깨진다.
- `polymer`가 망가지면 표현만 깨져야 한다.

## 3) 권장 코드 구조

```text
<package>/
├─ core/
│  ├─ service/
│  └─ domain/
├─ polymer/
│  ├─ PolymerBridge.java
│  ├─ item/
│  └─ block/
└─ mixin/
```

### `PolymerBridge` 책임

- `core` 데이터 -> Polymer API 입력 매핑
- 예외 발생 시 안전한 fallback 제공
- 로깅 포인트 표준화

### 금지

- `core` 서비스 안에서 Polymer API 직접 호출

## 4) 구현 루프

1. core 기능 완성
2. core 단독 검증
3. Polymer 어댑터 작성
4. 클라이언트 무설치 상태에서 접속/표현 확인
5. 예외/동기화 지연 점검

## 5) 성능/안정성 검증

체크 항목:

- 틱당 변환 횟수
- 반복 생성 객체(할당 압력)
- 동기화 지연(플레이어 수 증가 시)
- 예외 재발 빈도

권장:
- 고빈도 경로는 캐시/재사용 전략 적용
- 로그는 샘플링하거나 레벨 분리

## 6) 운영 장애 패턴

### A. 서버 상태와 표시 상태 불일치

- 증상: 아이템/블록 표현이 늦게 바뀌거나 롤백
- 원인: 상태 변경 이벤트와 Polymer 업데이트 타이밍 분리 실패
- 대응: 상태 변경 단일 진입점에서 표현 업데이트 트리거

### B. 버전 업 후 런타임 메서드 오류

- 증상: `NoSuchMethodError`, `ClassNotFoundException`
- 원인: Polymer API 시그니처 변경
- 대응: Polymer 호출부를 어댑터로 감싸고 변경 범위를 한 점으로 고정

### C. 대규모 접속 시 성능 저하

- 증상: 틱 지연, 간헐 렌더 동기화 실패
- 원인: 플레이어 단위 변환 로직 과다
- 대응: 변환 빈도 제어 + 필요 대상만 갱신
